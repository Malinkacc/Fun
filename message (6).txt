NZL Studio Obfuscator v3 (Z85-режим) — аудит уязвимостей + советы
Объект: nzl3_z85.lua (54 137 байт). Семпл №3: друг убрал VM и сделал упаковку Z85 → блочная перестановка → позиционный XOR → RC4 → loadstring(Lua-исходник).

Вердикт коротко: впервые в серии файл рабочий (компилируется, блоб полный, пайплайн цел). Но как защита — это шаг назад относительно VM-варианта: вся упаковка снимается одним статическим скриптом за секунды, а на выходе — читаемый Lua-исходник со всеми строками. Деобфускация выполнена полностью: payload.lua (1854 строки, отформатирован stylua).

Хронология взлома (статически, без рантайма)
В файле виден весь пайплайн: TH (Z85: z→!!!!!, разряды 52200625/614125/7225/85 — стандартный Z85-алфавит опознаётся мгновенно), zf (BE-u32 длина → 256-блочная перестановка → XOR (186+(i-1)*7)%256), sge (RC4, KSA+PRGA), затем loadstring.
Перестановка генерируется детерминированным LCG: сид 776059679, множитель 16807 (классический MINSTD) — константы в файле, таблицу даже не стали прятать (в v2 она была 256-байтной таблицей, тут вычисляется — компактнее, но так же вскрывается).
Ключ RC4 — 32 байта — лежит рядом: string.char(16+42,95+135,…) — «обфускация» суммами складывается в голове. Итоговый ключ: 3a e6 4e f6 71 9c e1 2f 4b 72 ac d0 6a 94 ab 76 …
Реализация пайплайна на Node: ~100 строк (decode.mjs), один запуск: n = 41 906 байт (доступно 41 984 — файл полный, 100.2%), payload компилируется в Luau и форматируется stylua без ошибок.
Результат: payload.lua — «BCW HUB v19 (Trepid Multi-Target)», тот же чит, что был в семпле №1. Полный разбор нагрузки — в payload_analysis.md.

Уязвимости
V3-1. Всё, что нужно для расшифровки, лежит в самом файле
Z85-алфавит — стандартный; сид LCG — константа; шаг/старт XOR — константы; RC4-ключ — рядом с шифртекстом (замаскирован школьными суммами). Криптография с ключом из того же файла — это не криптография, а кодирование. Вскрытие: один скрипт, ноль рантайма, ноль брутфорса.

V3-2. RC4 — сломанный шифр ещё с 2000-х
Даже если бы ключ не лежал рядом: RC4 имеет известные bias'ы (Fluhrer–Mantin–Shamir, key-scheduling biases), не выдерживает known-plaintext. А known-plaintext тут тривиален: payload начинается с -- BCW HUB v19 — известный заголовок даёт поток байтов.

V3-3. Payload — голый Lua-исходник
После расшифровки (5 секунд) — читаемый код: все имена RemoteFunction, таблицы урона данжей, URL библиотек UI. Не нужно ничего дизассемблировать — stylua и читай. VM-стадия из v2 отсутствует полностью. По стойкости это слабее v2: v2 требовала транскрипции 116 опкодов, v3 требует одного скрипта на 100 строк.

V3-4. Атрибуция содержимого в открытом виде
Первая строка payload: -- BCW HUB v19 (Trepid Multi-Target). Внутри — имена UI, репозитории библиотек. Обфускатор защитил обёртку, но не скрыл сам продукт.

V3-5. Нулевой анти-анализ
Ни проверки окружения, ни таймингов, ни ловушек, ни целостности. Расшифрованный payload можно патчить и запускать напрямую, минуя обёртку.

V3-6. Мелочи
loadstring на выходе требует разрешения в среде (в Roblox — включённый loadstring) — лишняя зависимость от окружения;
длина блоба BE-u32 — ок, но нет никакой проверки целостности (HMAC) — подмена/битность не детектится;
обёртка return(function() ... end)() — косметика.
Что стало ЛУЧШЕ по сравнению с v1/v2 (честно отметим)
Файл впервые работает: компилируется (проверено Luau-компилятором), длина совпадает, стадий расшифровки на месте. Roundtrip-тесты, видимо, появились — так держать.
Z85 вместо \ddd-эскейпов: файл вдвое компактнее при том же payload.
Перестановка через LCG вместо явной 256-байтной таблицы.
Ключ размазан по 4 кускам с суммами — хотя это всё ещё не защита.
СОВЕТЫ АВТОРУ (раунд 3)
1. Верни VM-стадию из v2 — теперь она бы сработала
Твоя v2 уже содержала правильную идею (кастомный байткод + интерпретатор), а v3 наконец научилась эмитить рабочий файл. Скрести их: v3-упаковка → v2-VM-байткод (вместо loadstring(lua_source) — run_vm(bytecode)). Тогда аналитику придётся: снять упаковку (легко) И транскрипцировать интерпретатор (вечер работы) — уже реальный порог. Сейчас v3 снимается скриптом на 100 строк целиком.

2. Убери ключ из файла — или признай, что это кодирование, а не шифрование
Минимум: вычислять ключ из свойств, которых нет в файле. Нормально: серверная выдача (hwid/лицензия → HTTPS → ключ), файл без сети бесполезен.RC4 с ключом из файла не защищает ничего — только задерживает на минуты.

3. Хоть какая-то настоящая криптостойкость
RC4 выбросить. Для Lua-friendly: XOR-поток в режиме CBC (каждый блок зависит от предыдущего
IV), ключ из пункта 2; или keystream = hash(key || counter) самодельный — всё равно лучше голого RC4.
Известный заголовок payload (-- BCW HUB…) — это подарок для known-plaintext. Убери комментарии из зашифрованной части или добавь случайный префикс перед контентом.
4. Рандомизируй параметры упаковки персемплно
Сейчас: сид LCG 776059679, старт XOR 186, шаг 7 — константы для всех файлов. Один раз написал декодер — читает все твои файлы. Делай сид/старт/шаг (и порядок слоёв!) случайными на каждый билд и выводи их в файле неявно (например, выводимыми из первых байтов блоба).

5. Целостность и окружение
HMAC/hash(payload) с ключом — подмена детектится;
не падай сразу при несовпадении — порти результат через N инструкций (аналитик потратит время);
проверка, что payload запущен из твоей обёртки (например, обёртка передаёт маркер в замыкание), чтобы расшифрованный исходник нельзя было просто сохранить и запустить.
6. Продолжай roundtrip-тесты
Единственный семпл, который не сломался — тот, где ты, судя по всему, стал проверять вывод. Формализуй: эталонный набор скриптов (функции/замыкания/varargs/строки с кавычками/длинные конкатенации) → обфускация → compile + запуск + сравнение поведения. Это уже спасло v3 — не останавливайся.
