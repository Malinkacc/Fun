# Разбор «защищённого» скрипта: деобфускация, алгоритм и найденные ошибки

**Что было на входе:** 4 «строки» кода — это шифровальщик строкового литерала + десериализатор
байткода + интерпретатор (VM) + запуск скрытой функции `r1("<блоб ~80 КБ>", <ключ>)`.

**Что сделано:** код переписан в читаемый вид, «шифр» снят и описан, формат байткода разобран
по байтам, все 116 опкодов распознаны и подписаны, деобфусцированная VM **проверена запуском**
и сравнением с оригиналом, собран инструмент для вскрытия второго слоя (самой полезной нагрузки).

---

## 1. Коротко (TL;DR)

| Вопрос | Ответ |
|---|---|
| Что это такое? | Самодельный обфускатор формата «зашифрованный blob → свой байткод → свой интерпретатор». Классическая схема `loadstring`-обёрток (стиль Roblox/Luau-эксплойтов). |
| Это хорошая защита? | Нет. Шифр — фиксированная перестановка байт + XOR с константой `0xE1`, без ключа. Снимается за секунды (инструмент в этой же папке). |
| Скрытый код видно? | Он лежит в литерале ~80 КБ. Из **присланного текста** его достать нельзя — литерал повреждён вставкой (см. §7.1), но в исходном файле он целый: запусти `unpack_stage2.lua`. |
| Скрипт вообще работает? | В присланном виде — **нет**: падает на первом же шаге (`t1` не определена). Плюс часть опкодов зовёт несуществующие функции, а сам код требует `bit32`. |

## 2. Структура оригинала

```
┌────────────────────────── 4 «строки» присланного скрипта ──────────────────────────┐
│                                                                                    │
│  H4()   — склейка кусков строки (по сути table.concat)                              │
│  q1()   — «расшифровка» литерала: перестановка 256-байтных блоков + XOR → t1(plain) │
│  h4/c1/C4 — чтение u32 / i32 / float64 (little-endian)                              │
│  W4()   — десериализатор контейнера байткода (вложенные прототипы)                  │
│  w4()   — интерпретатор (VM) на 116 опкодов                                         │
│  r1()   — обёртка: q1 + W4 → функция                                                 │
│  protectedFn()  ← запуск                                                            │
└────────────────────────────────────────────────────────────────────────────────────┘
Поток данных:  blob-литерал ──q1──▶ байты байткода ──t1──▶ W4 ──▶ VM(w4) ──▶ «полезный код»
                                                        ▲
                                          t1 — ВНЕШНЯЯ функция, в файле её нет
```

Имена в оригинале обфусцированы (`Q4`, `v4`, `P4`, `e4`, `E1`, `Y4`, `I4`, `W4`, `w4`, `q1`…),
а внутри VM ещё и «зашиты» мусорные ветки — см. §7.2.

## 3. Как устроено «шифрование» (полностью)

Формат блока (`A4` в `q1`):

```
байт 1..4 : длина N (big-endian: b1*2^24 + b2*2^16 + b3*2^8 + b4)
байт 5..  : тело, длина тела = ceil(N/256)*256  (выравнивание по 256 обязательно!)
```

Снятие обфускации — два шага.

**Шаг 1. Перестановка внутри каждых 256 байт** по встроенной таблице `I4`
(это полная перестановка чисел 0..255 — проверено):

```lua
for i = 1, N do
  local block = math.floor((i - 1) / 256)
  local slot  = (i - 1) % 256
  shuffled[i] = body[ block * 256 + SHUFFLE[slot + 1] + 1 ]   -- +1: Lua-индексация
end
```

**Шаг 2. XOR с повторяющимся ключом** (период 256, байты 225, 226, …, 224):

```lua
for i = 1, N do
  plain[i] = shuffled[i] ~ ((i - 1 + 225) % 256)   -- 225 = 0xE1
end
```

**Шаг 3.** `return t1(plain, q4)` — «расшифрованный» результат **отдаётся наружу** во внешнюю
функцию `t1`, которой в файле нет.

**Про «ключ»:** в вызове `r1(blob, H4({"\222\248p1","u4\153b\154","\223\001\255x","0W\017\162"}))`
вторым аргументом идёт 17-байтная строка (`DE F8 70 31 75 34 99 62 9A DF 01 FF 78 30 57 11 A2`),
она доезжает до `q1(..., q4)` — **и нигде не читается**. Это декорация: реальный «ключ» —
константа `225` плюс фиксированная таблица перестановки.

**Размер присланного блока:** судя по началу литерала (`\000\001\057n…`), заявленная длина
`N = 80 238` байт; телу требуется `ceil(80238/256)*256 = 80 384` байт, т.е. последние 146 байт
блока — «пустое место» (это нормально для схемы, но нигде не проверяется — см. §7.2).

## 4. Формат контейнера байткода (`W4`)

```
u32  numParams            число параметров
u8   isVararg             0/1
u32  maxStack             (читается, но нигде не используется!)
u32  nUpvals              количество upvalue-описателей
     для каждого: u8 flag + u32 index
       flag=1 → upvalue ссылается на РЕГИСТР внешней функции (открытый upvalue)
       flag=0 → upvalue ссылается на upvalue #index внешней функции
u32  nConsts
     для каждой: u8 tag
        0 — nil
        1 — bool  (+1 байт)
        2 — number (+8 байт, IEEE754 double LE)
        3 — string (+u32 длина + байты)
        4 — ссылка на вложенный прототип (+u32 индекс)
u32  nInstrs
     каждая инструкция — 8 байт: op(1) A(1) B(1) C(1) D(i32 LE)
u32  nProtos
     далее рекурсивно вложенные прототипы в том же формате
```

Операнд `D` — индекс константы (0-based), подтверждено на всех опкодах, работающих с константами
(`LOADK`, `GETGLOBAL`, `GETTABLEKS`, `ADDK`, `EQK`, `JUMPIFEQK`, …).

Фрагмент реального вывода дизассемблера (на тестовом чанке):

```
-- proto #1: params=0 vararg=false maxstack=45 upvalues=0
--   K1 = "alpha"
--   K2 = "beta"
--   K3 = "x"
--   K4 = "print"
--   K5 = "|"
--   K6 = 1.0
[   1] NEWTABLE       A=0 B=0 C=0 D=0
[   2] LOADK          A=1 B=0 C=0 D=0   -- K1 = "alpha"
[   3] APPEND         A=0 B=1 C=0 D=0
[   4] LOADK          A=1 B=0 C=0 D=1   -- K2 = "beta"
...
[  60] GETGLOBAL      A=33 B=0 C=0 D=3   -- K4 = "print"
[  61] CALL           A=33 B=2 C=0 D=0
[  62] RETURN         A=0 B=0 C=0 D=0
```

Полная таблица всех 116 опкодов с именами и примечаниями — в **`deobfuscated/opcodes.md`**.

## 5. Что было проверено запуском (а не только «прочитано глазами»)

Анализ делался статически + динамически (Lua-совместимый интерпретатор). Проверки:

1. **`decryptBlob` ↔ шифрование** — обратное преобразование (перестановка + XOR) реализовано и
   прогнано по кругу: 4 тестовых блока зашифрованы «как в оригинале» и корректно расшифрованы.
2. **Деобфусцированная VM сравнивалась с оригинальной** на 4 синтетических чанках — **поведение
   идентично** (то же число, та же строка на выходе, та же ошибка на ошибке). Это гарантия, что при
   переписывании ничего не потерялось:
   * чанк 1 (таблицы, `table.concat`, строки, битовые операции, сравнения, `TYPE`/`SIGN`) — одинаковый вывод;
   * чанк 2 (замыкание + открытый upvalue: `CLOSURE` 214 → `GETUPVAL` 14 → `ADDK` 208) — обе VM печатают `42.0`;
   * чанк 3 (инструкция с **неизвестным опкодом 250**) — обе VM молча её пропускают (см. §7.2);
   * чанк 4 (вызов `math.z2`) — обе VM падают с одинаковой ошибкой `attempt to call a nil value (field 'z2')`.
3. **Инструмент `unpack_stage2.lua`** протестирован на «имитации» исходного файла (та же структура
   `r1("…", H4({…}))`): литерал извлечён → блок расшифрован → контейнер разобран → выведены
   константы и листинг.
4. `bit32`-fallback (нужен, потому что современный Lua 5.4 и fengari библиотеку не содержат) сверен
   с эталонными вычислениями на 54 наборах аргументов для 8 функций — полное совпадение.

## 6. Второй слой: что внутри и как достать

Внутри — **байткод** того самого формата, что разбирает `W4`, т.е. код-полезная нагрузка
(обычно это «загрузчик»: сеть/`loadstring`/подмена окружения). Прямо из присланного сообщения его
достать нельзя: текст литерала пострадал при вставке (§7.1). Но в исходном файле он целый.

### Как вскрыть (безопасно, без запуска байткода)

```bash
cd deobfuscated
lua unpack_stage2.lua /путь/к/protected.lua out/
```

Что получится:

* `out/stage2.bin` — сырые байты байткода (например, для `xz`/бинанализа);
* `out/stage2.dis` — читаемый листинг: номера прототипов, их параметры, пул констант,
  каждая инструкция с именем и расшифрованной константой;
* на экран — все строковые константы (адреса, имена, ключи) и сводка.

На что смотреть в первую очередь:

* строковые константы — там обычно лежат URL/Host/токены;
* `GETGLOBAL (133)` с именами `loadstring`, `require`, `load`, `pcall`, `game`, `http`, `request`,
  `socket`, `io` — выдаёт сетевой/инжектирующий загрузчик;
* `SETGLOBAL (157)` / `SETMETATABLE (252)` — payload что-то меняет в окружении;
* наличие опкода **9** — «мина» `while true do end` (см. §7.2).

Инструмент **не исполняет** байткод — только разбирает. Файл `vm.lua` — сама VM, если понадобится
исполнить/пошагово отладить (или дописать декомпилятор).

## 7. Найденные ошибки

### 7.1. Критические — из-за них код не работает как прислан

1. **Вызов неопределённой функции `t1`.** В `q1` последняя строка — `local e1=t1(y1,q4)`.
   Ни определения, ни параметра, ни импорта: `t1` — «висячая» глобальная переменная.
   Результат — `attempt to call a nil value (global 't1')` **сразу после расшифровки**.
   Т.е. вся конструкция рассчитана на внешний загрузчик, который потерян (или оборван при копировании).
   Заодно это значит, что «защита» не самодостаточна.

2. **Артефакты вставки, ломающие синтаксис (и данные).** В присланном тексте:
   * `&gt;` / `&lt;` / `&amp;` вместо `>` / `<` / `&` — и в коде, и **внутри литерала**;
   * `or *G` вместо `or _G` (нижнее подчёркивание «съела» разметка);
   * `[bit32.band](http://bit32.band)` вместо `bit32.band`.

   Если это содержимое файла — он просто не компилируется (а `*G` и ссылка — вообще не Lua).
   Для литерала это означает, что байты после расшифровки дадут мусор. Поэтому **расшифровка
   присланного текста невозможна в принципе** — нужен исходный файл (см. §6).

3. **Жёсткая зависимость от `bit32` без fallback.** `bit32.bxor/band/bor/bnot/lshift/rshift/...`
   вызываются в самом начале (`q1`) и во множестве опкодов. Но `bit32` **нет в стандартном Lua 5.1** (и не во всех сборках LuaJIT),
   а в **Lua 5.4 удалена**. Там код падает сразу: `attempt to index a nil value (global 'bit32')`
   (проверено). Работает только в Lua 5.2/5.3/Luau/Roblox-окружениях.

4. **Несуществующие функции «стандартной» библиотеки.** Диспетчер вызывает имена, которых нет ни в
   стандартном Lua, ни в Luau: `string.W1`, `string.S1`, `string.C2`, `string.m2`, `string.V1`,
   `math.M2`, `math.h2`, `math.k2`, `math.y2`, `math.z2`. Соответствующие опкоды (46, 52, 68, 85, 112,
   163, 176, 189, 243, 244) на любой нормальной сборке упадут с `attempt to call a nil value`
   (проверено на `math.z2`). Это не защита, а поломка: код рассчитан на «пропатченное» окружение
   либо собран обфускатором, который переименовал функции библиотеки, но не восстановил их при запуске.

5. **`getfenv` не существует в Lua 5.2+.** В `w4` окружение берётся как `getfenv and getfenv() or _G`;
   на Lua 5.4 `_G` даёт другое окружение, чем ожидалось автором (глобальные записи уйдут «не туда»).

### 7.2. Логические и архитектурные ошибки

6. **«Ключ» не используется.** 17-байтная строка передаётся в `r1/q1`, но ни один байт её не читается.
   Защита = фиксированный XOR, т.е. обратима кем угодно (демонстрация — `unpack_stage2.lua`).

7. **Нет проверок границ при чтении блока.** `A4:byte(1..4)` и `body:byte(srcPos)` на коротком
   (обрезанном) литерале вернут `nil`, и получится `attempt to perform arithmetic on a nil value`
   вместо внятной ошибки. Проверка «длина литерала ≥ 4 + ceil(N/256)·256» отсутствует —
   а она нужна обязательно из-за шага перестановки (см. §3).

8. **Декодер не проверяет конец данных.** `h4/c1/C4` читают 4/8 байт без контроля `#data`; любой
   обрыв даёт «голый» runtime error; отсутствует и проверка числа прототипов (`K4`) на разумность.

9. **Неизвестные опкоды игнорируются молча.** Цепочка `if/elseif` без `else`: инструкция с
   незарегистрированным кодом просто пропускается. Проверено: опкод `250` не делает ничего, и
   выполнение продолжается дальше. Это делает поведение повреждённого (или чужого) байткода
   непредсказуемым и убивает диагностику.

10. **Мёртвый код и дубликаты в диспетчере.** 9 обработчиков — пустышки (`local x = N4[0]` /
    `local x = nil`): коды **44, 81, 86, 96, 146, 164, 170, 178, 205**. Ещё 8 пар обработчиков
    полностью дублируют друг друга: **4=141, 26=165, 121=16, 136=91, 148=29, 183=209, 196=144, 44=81**.
    Это «наполнитель» для запутывания: он раздувает таблицу до 256 номеров (140 не используются вовсе),
    но ничего не делает.

11. **Опкод 9 — антиотладочная мина:** `while true do end`. Если такой байткод есть в реальной
    нагрузке, интерпретатор зависает намертво (и вырваться нельзя — внутри VM нет никаких проверок
    времени/квоты). Такой же эффект возможен и случайно, если считать повреждённый байткод.

12. **Опкод 43 и 182 — константный мусор:** `(#tostring(type(nil))==4)` → всегда `false`,
    `(#tostring(type(nil))==3)` → всегда `true`. Это не операции, а выброшенные строки.

13. **Опкод 87 — сомнительная семантика:** `N4[u4]=N4[u4]-N4[u4+2]` (затирает регистр!) плюс
    условный переход. Похоже на ошибку/переусложнение (в Luau-байткоде аналога нет);
    пользоваться им в реальной нагрузке нельзя.

14. **Регистрами служит обычная Lua-таблица.** Нет проверки/лимита номера регистра, нет очистки
    (на длинных скриптах таблица разрастается), все обращения — хеш-табличные (в разы-десятки раз
    медленнее массива), плюс каждый опкод — это 116-звенная цепочка `if/elseif` (линейный поиск).

15. **Утечки памяти через замыкания.** Опкод 214 (`CLOSURE`) создаёт `g1[c2]={u1, i2.d2}` —
    ссылку на **всю** таблицу регистров родителя; она живёт, пока живёт замыкание, и никогда не
    освобождается. Долгая работа такого «скрипта» = рост памяти и удержание больших объектов.

16. **Нет обработки ошибок.** `protectedFn()` вызывается без `pcall/xpcall`, и в байткоде нет
    защищённого вызова. Любая ошибка (а она гарантирована — см. §7.1) валит хост-программу и
    оставляет невнятный traceback.

17. **Квадратичные алгоритмы.** Оба цикла расшифровки собирают строку через
    `C1 = C1 .. string.char(...)` и `y1 = y1 .. string.char(...)` — это O(n²) на 80 КБ; правильно —
    таблица + `table.concat`.

18. **Мёртвые сущности.** Объявлены и не используются: `P4` (`string.char`), `e4` (`table.insert`),
    `Y4` (`bit32.bxor`), `local a5` в `w4`, второй параметр `q1`/`r1`, `f4` в разборе инструкций.
    `H4` — ручная замена `table.concat`.

### 7.3. Замечания по безопасности (что важно понимать)

19. **Обфускация ≠ защита.** Перестановка + XOR с константой снимаются автоматически; ключ в коде
    не участвует. Любой, кто имел доступ к файлу, получит ваш байткод.
20. **Нет проверки целостности.** Подменив blob, можно заставить чужой код исполниться в вашем
    окружении (подписи/хеша нет).
21. **VM даёт нагрузке доступ к окружению:** опкоды 133/157 читают/пишут **глобальные переменные**
    (`env[K[D+1]]`), 80/252 работают с метатаблицами. Т.е. «полезный код» может править глобалы
    процесса — типичный приём эксплойтов/читов (Roblox-эксплойты: `game:HttpGet`, `loadstring`,
    подмена функций игры).
22. **Рекомендация:** не запускать вне песочницы. Если очень нужно — запуск только с перехватом
    `load`/`loadstring`/сетевых функций, в отдельной виртуалке без доступа к вашим данным.
    Для статического анализа — пользоваться приложенными инструментами (они ничего не исполняют).

## 9. Чтобы я довёл разбор до конца

Пришлите **сам файл** скрипта (или только blob-литерал в `.txt`), либо вывод инструмента:

```bash
lua unpack_stage2.lua protected.lua out/ > log.txt 2>&1
```

По `out/stage2.dis` + `log.txt` я разберу второй слой: восстановлю структуру функций, деобфусцирую
листинг в псевдокод и скажу точно, что payload делает (и чего в нём опасного).
